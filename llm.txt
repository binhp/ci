This file is the full spec a coding agent follows to build the AI code verification pipeline.

ROLE
Principal DevSecOps Architect. Standards: CIS Docker Benchmark v1.6, SLSA Build L2,
OWASP Top 10 2025 (and 2021 for old rule ids), OWASP ASVS 5.0, OWASP MASVS (ios/react-native),
CWE Top 25 (2025), NIST SSDF SP 800-218, OWASP Top 10 for LLM Applications 2025.
Write production code, not examples.

Each profile must:

GOAL
Harden the AI code-review pipeline. It joins 6 scan groups in one run: secrets,
dependencies and SBOM, SAST, lint and quality rules, AI guardrails, docs lint.
SUPPORTED STACKS: java, js, react (sub-profile of js), ios, python, go. One PROFILE
section per stack (PROFILES, section 10). The other sections hold every rule that is not
stack-specific.
The pipeline verifies AI-generated and human code on 4 axes. Together they form the
quality gate (section 4c):
  security        secrets, CVEs, SAST, supply chain, CI hardening, agent-config safety.
  reliability     bugs, null and error handling, compile and type errors, timeouts.
  maintainability complexity, size, duplication, SOLID, dead code, naming.
  tests           coverage on new code, test integrity, tests that go with code changes.
Each rule belongs to one axis (registry, section 4h). A failure on any axis fails the run.
The pipeline must run offline (air-gapped), non-root, read-only. It must produce SARIF reports for CI
upload. It must detect the project language and source roots at runtime. Do not hardcode **/src.

TRUST MODEL
- Trusted: the image (by digest, signed), the base branch, files reviewed by a CODEOWNER.
- Untrusted: the PR or diff under scan, everything in /src, build output, tool output
  derived from repo code, the CI cache written by a PR job.
- Rules:
    1. The code under scan cannot change the rules that judge it. Rules, lint config,
       ignore files and the gate come from the image. Data files come from the base commit.
    2. Repo code that runs (the Java build) runs in a separate container (stage 1). It
       cannot write summary.json or SARIF. Limit: it can fake its own compile result;
       G3 makes a human review each build-logic change (section 7).
    3. Git in the container runs no hooks and no fsmonitor.
    4. The trivy DB and package data are inside the image. No writable cache can change them.
    5. On a PR, CI runs only base-branch copies of ai-review.sh, doctor.sh, image.ref and
       versions.lock.json (section 9).
- Limit: on GitHub `pull_request`, a PR can edit the workflow file. Only CODEOWNERS review
  and an org ruleset or required workflow stop that (section 9). State it in --help.

INPUTS — NONE REQUIRED. The agent resolves every version, URL, digest and checksum itself.
It queries upstream at generation time (rule R below). The user may supply OPTIONAL overrides.
A missing override is never a reason to stop or ask.
A missing host tool is never a reason to stop or ask. Section P detects and installs it.
Optional overrides (defaults as shown):
  - distro: alpine | debian-slim            (default: debian-slim; JDK/Node/SwiftLint need glibc)
  - mirror base URL                         (default: none = upstream; with a mirror, fetch the same
                                             files from it and re-verify)
  - pin overrides: TOOL=x.y.z               (default: latest stable passing the cooldown)
  - release cooldown days                   (default: 7)
  - quality thresholds                      (default: section 4c)
  - stacks: java,js,react,ios,python,go     (default: all; the agent builds only these profiles)
Tools to resolve (the agent finds the official release source of each):
  secrets: gitleaks. deps/SBOM: trivy. SAST: semgrep (pip, hash-pinned) + rules in this repo.
  docs: vale, markdownlint-cli2 (+ lychee optional, offline link check).
  duplication: jscpd (npm). CI: zizmor, actionlint.
  Per stack: TOOLS in each PROFILE section.
  Do not use SonarQube/SonarScanner (needs a server). Use the Sonar-equivalent rules in section 4.

R) AUTO-RESOLUTION (replaces all manual input; the agent runs it, not the user)
Deliver .ai-review/resolve.sh (host, needs network, run once and on a schedule). It writes
.ai-review/versions.lock.json (committed, reviewed in a PR like any dependency bump).
Dockerfile build args, ai-review.sh and README READ the lock file.
- Latest version: query the official source. Do not use a search engine or memory.
    GitHub releases:  `gh api repos/<owner>/<repo>/releases/latest` (stable only: skip
                      draft/prerelease; apply the cooldown by `published_at`).
    npm:              `npm view <pkg> version time --json`.   PyPI: `/pypi/<pkg>/json`.
    Maven Central:    `maven-metadata.xml` (release, not SNAPSHOT/alpha/beta/rc).
    Go tools:         GitHub releases.
  Skip a version younger than the cooldown. Use the previous stable and log it.
- URL: build it from the release asset list for linux/amd64 (and linux/arm64 if asked).
  Do not use a hand-written template. If an asset is missing, exit 2 with the asset names found.
- Verify all of these. Each failure exits 2 (never a warning, never `|| true`):
    1. SHA256 of the downloaded file equals the checksum published by the release (checksums
       file) AND equals GitHub's asset `digest` field when the API returns one.
    2. Signature or attestation, only where upstream publishes one (cosign
       `verify-blob` / `gh attestation verify`). State per tool in Assumptions: "signature
       verified" or "upstream publishes none; integrity only". Do not claim more.
    3. `<tool> --version` output equals the resolved version.
    4. Archive has no path traversal (`tar -tf` check) before extraction.
    5. For npm/PyPI/Maven: resolve exact versions. Then write the lockfile with integrity
       hashes (`npm ci`-compatible package-lock.json, `pip-compile --generate-hashes`,
       Maven checksums via `--strict-checksums`). Install from the lock with
       `--ignore-scripts` / `--require-hashes`.
    6. Release is not yanked/deprecated. The project has no open critical advisory for
       that version (query the GitHub advisory API; if it fails, exit 2).
- Base image: resolve the newest patch tag of the chosen distro line (e.g. debian
  `stable-slim`) to its digest with `docker buildx imagetools inspect` (or `crane digest`).
  Write `image@sha256:…` into the lock file. If the image has a cosign signature, verify it.
- Trivy DB: run `trivy image --download-db-only` and `--download-java-db-only` into
  .ai-review/.cache/trivy. Record DB `UpdatedAt` and the SHA256 of each DB file in the lock
  file. build.sh bakes the DB into the image (section 1). If the DB is older than
  14 days, fail the later scan (exit 2) (override: AI_REVIEW_MAX_DB_AGE_DAYS). The publish
  job (section 9) rebuilds weekly. 14 days gives 7 days to merge its PR. After 10 days,
  the scan prints a warning "trivy DB is <n> days old: merge the publish PR".
- OS package snapshot: record a snapshot.debian.org timestamp (or the Alpine repository
  tag) in the lock file. The Dockerfile installs OS packages from it.
- Package data for G1: write .ai-review/.cache/data/<ecosystem>-index.json and
  <ecosystem>-top.txt (section 5, G1). Record each source URL and SHA256 in the lock file.
- Signing identity: record the cosign keyless identity (issuer, subject regex) of the
  publish job in the lock file. CI verifies the image against it.
- `--seed-java`: fill the Java cache (PROFILE: JAVA, PROFILE RULES). Run it only on a trusted ref.
- Lock file schema: .ai-review/schema/versions.lock.schema.json. resolve.sh validates its
  output against it before it writes. Top-level keys: schema_version, generated_at,
  cooldown_days, base_image, os_snapshot, tools[], npm, pypi, maven, actions[], trivy_db,
  data[], signing. Each tool: {name, version, published_at, url, sha256, signature:
  verified|none, source}.
- Runtime image ref: after `docker buildx build`, write the digest to
  .ai-review/image.digest. ai-review.sh reads AI_REVIEW_IMAGE, else that file. Nobody types it.
- Idempotent: if upstream is unchanged, two runs of resolve.sh produce an identical lock
  file. Output a human diff of changes (old → new version, published_at, checksum).
- Failure handling: on network error, rate limit, missing checksum or mismatch, exit 2 with the
  URL and the reason. Retry 3 times with backoff on 5xx/429 only.
- Do not invent a value. Do not write a value not obtained from a live query in this run.

P) HOST PREREQUISITES (auto-detect, auto-install; the user needs no prior knowledge)
Deliver .ai-review/doctor.sh. It finds each host tool the pipeline needs. It installs the
missing ones or prints exact steps for this OS. The user does not read a list or pick a package.
- Callers. resolve.sh, build.sh, ai-review.sh, tests/smoke.sh and `--init-ci` run
  `.ai-review/doctor.sh --need <phase>` first. Non-zero → stop with the same code.
  Do not keep a second tool list in any other file.
- Flags: --need resolve|build|scan|ci|all (default all). --plan (print only, change nothing).
  --yes (install with no prompt, for CI and agents). --json (machine output). -h/--help.
- Detect the host. Do not ask the user:
    OS:      `uname -s` → Darwin | Linux | MINGW*/MSYS*/CYGWIN* (native Windows).
    Distro:  `ID` and `ID_LIKE` from /etc/os-release. WSL2: "microsoft" in /proc/version.
    Arch:    `uname -m` → amd64 | arm64.
    Manager: first found of brew, apt-get, dnf, yum, apk, pacman, zypper.
    Rights:  root, or `sudo -n true` works, or no sudo.
    Network: one HTTPS HEAD to the first upstream in the lock file (or github.com), 5 s timeout.
    CI:      `CI`, `GITHUB_ACTIONS`, `GITLAB_CI`, `JENKINS_URL` set → non-interactive.
- Tools per phase. Build this table from the commands the other files run on the host.
  Do not copy it from README. Each tool counts as present only if its version command passes:
    scan:    bash, git, docker (daemon reachable: `docker info`).
    ci:      scan tools.
    build:   scan tools, docker buildx, cosign.
    resolve: build tools, curl, jq, gh, tar, a SHA256 tool, crane (only if buildx
             imagetools is missing). npm, pip-compile, mvn: only for stacks found by
             detect_project() (section 2), and only if resolve.sh runs them on the host.
             If resolve.sh runs them in a pinned container, do not list them.
  ci also needs cosign (image signature check, section 9).
  Minimum version per tool = the first release with every flag and subcommand the scripts
  use (for example `gh attestation verify`, `docker buildx imagetools`). Read it from the
  tool's release notes at generation time. Record it and the source URL in Assumptions.
  If a tool is older, treat it as missing.
- Host scripts (doctor.sh, resolve.sh, build.sh, ai-review.sh, smoke.sh) run on bash 3.2
  (macOS default). No `declare -A`, no `mapfile`, no `${x,,}`. SHA256: `sha256sum`, else
  `shasum -a 256`. No GNU `timeout` on the host. These rules remove three prerequisites.
- Install order for one missing tool. Stop at the first step that works:
    1. OS package manager. Map tool → package name per manager in one table in doctor.sh.
       Confirm the package exists before the plan (`brew info --json=v2`, `apt-cache policy`,
       `dnf info`, `apk search -e`, `pacman -Si`, `zypper info`). Do not guess a name.
    2. Official release binary: resolve it with rule R (latest stable, cooldown, SHA256 vs.
       published checksums, signature where published). Install to "$HOME/.local/bin".
       No sudo. If that directory is not on PATH, print the one line to add to the shell rc.
    3. Neither works → print the official install page URL and the exact commands. Exit 2.
- Special cases:
    macOS, no brew: download the Homebrew .pkg from the Homebrew GitHub release with rule R.
      Install it with `sudo installer -pkg <file> -target /`. If no .pkg asset exists, use
      step 3. Do not run the `curl | bash` one-liner.
    macOS, no docker: install the colima, docker and docker-buildx formulae. Run
      `colima start --cpu <n> --memory <GiB>` with n ≥ AI_REVIEW_CPUS + 1 and GiB ≥
      AI_REVIEW_MEMORY + 2 (section 7). If colima runs with less, print the restart command.
      Reason: Docker Desktop needs a GUI license accept on the first run. If Docker Desktop
      is present but stopped, run `open -a Docker` and wait 60 s for `docker info`.
    Linux, docker present, daemon stopped: `sudo systemctl start docker` (systemd), else
      print the start command for the init system found.
    Linux, docker socket denied: `sudo usermod -aG docker "$USER"`. Tell the user to log in
      again, or run `newgrp docker`. Rootless Docker counts as present.
    Linux, no docker: distro package (docker.io, moby-engine or docker). If the distro has no
      package, use step 3 with the Docker Engine page for that distro.
    gh not logged in and GH_TOKEN, GITHUB_TOKEN unset: in a TTY, run `gh auth login --web`.
      In CI, exit 2 with "set GH_TOKEN". Only the resolve phase needs this.
    Native Windows (MINGW/MSYS/CYGWIN): do not install. Print the WSL2 steps: run
      `wsl --install` in an admin PowerShell, restart, open the Ubuntu shell, run the script
      again there. Exit 2.
    No network: do not install. Print the plan and the mirror override (INPUTS). Exit 2.
      The scan phase is offline. It needs no install if the image is loaded.
- Consent. Print the full plan first: tool, found version, action, exact command.
    No change needed → exit 0, no prompt.
    TTY, no --yes → ask one question: "Install N tools? [y/N]". Default no.
    Non-TTY, no --yes → do not install. Print the plan. Exit 2.
    --yes → install. Print each command before it runs. Do not hide sudo.
    CI scan jobs use --plan only (section 9). They do not install.
  Do not install anything the phase does not need. Do not upgrade a tool that passes.
- After the installs, run the detection again. A tool still missing → exit 2 with its fix.
- Output: a table on stderr (tool | need | found | status | fix). With --json, the same
  data on stdout. The script writes .ai-review/.cache/doctor.json (OS, arch, manager, tools).
- Exit policy: 0 = all present, 2 = a tool is missing or did not install. No other code.
- Idempotent: a second run on a ready host prints "ready" and changes nothing.
- Limits. State them in --help and in Assumptions:
    `gh auth login` needs the user once, unless GH_TOKEN is set.
    Docker group membership starts only after the user logs in again.
    Package-manager tools are not hash-pinned like lock-file tools. Trust = the manager's
    signed index. Release-binary installs (step 2) are hash-checked.
    Native Windows without WSL2 is not supported.

DELIVERY
Send the common files first, in tree order. Then each selected profile's files, in
PROFILES table order. Send files in tree order. Wait for "next" before each message. One file per message,
except: send up to 4 config files of < 80 lines each in one message (lint/*, schema/*,
the starter data files). Each file still gets its own Assumptions and Validate block.
Before the first file, detect this host with the section P rules. Do not ask the user for
the OS or the tools. Report OS, arch, manager and each tool found or missing.
Before each "## Validate" block, install the missing tools with the section P order.
Ask before sudo. If a tool cannot be installed, mark each command that needs it NOT RUN
(missing: <tool>; fix: <command>).
Each message contains (WRITING STYLE applies):
  a) "## Assumptions": tool version → exact subcommands/flags used
  b) the complete file
  c) "## Validate": exact commands, each marked RAN / NOT RUN (reason)
The last message ends with:
  - "## Build": docker buildx build --provenance=true --sbom=true --platform linux/amd64
    --build-arg … ; write the digest to .ai-review/image.digest (no manual copy). Local
    builds are SLSA L1 at most. Signed L2 builds come from the publish job (section 9).
  - "## CI": run `./ai-review.sh --init-ci auto` and show the result. Ask the user one
    question: add it to CI now? If yes, run it with --write. Mark each command RAN / NOT RUN.
  - Threat-model table: risk → control → file:line → SSDF group (PO/PS/PW/RV, NIST SP
    800-218) → OWASP Top 10 2025 category → axis. One row per TRUST MODEL rule.
    Add a SLSA row: level claimed and evidence. L2 needs signed provenance from a
    tamper-resistant build platform. Do not claim without evidence.

GLOBAL RULES
- No placeholders, no TODOs, no "…", no `|| true`, no `curl | sh`.
- Scripts: shellcheck clean. Dockerfile: hadolint clean. YAML: yamllint clean.
- No tool reads from the network at scan time.
- Every tool skips .ai-review/ (its own cache and reports).
- No tool reads a config or ignore file from the scanned repo (TRUST MODEL).
- Diff mode scans committed HEAD only. Say so in --help.
- Detect language and scan roots at runtime. Do not hardcode **/src.
- Writing style: every message, --help text, log line, error message and comment in the
  generated files follows WRITING STYLE below.

WRITING STYLE (STE plus caveman, source <https://github.com/juliusbrussee/caveman>, Apache-2.0)
This section is the source for the style rules. A repo AGENTS.md links here. It does not copy them.
- Answer first: `[thing] [action] [reason]. [next step].`
  Write "trivy DB stale: 16 days. Run resolve.sh." Do not write "It seems that the DB...".
- One idea per sentence. Procedure sentence ≤ 20 words. Descriptive sentence ≤ 25 words.
  Active voice. Condition before command. One word for one thing.
- Drop: articles in lists and messages, greetings, "let me", recaps.
- Drop filler words: "in order to", "please", "note that", "it is important", "basically".
- Keep articles in a procedure sentence if the meaning is not clear without them.
- Do not change a rule, a value or a name when you shorten text.
- Keep: "not", "no", "never", "only". Numbers with units. Rule ids.
- Payload verbatim: code, commands, paths, flags, error text from a tool, character for
  character.
- No fake caveman words. If the short form is not shorter, use the plain form.
- Full sentences for a security warning, an irreversible action and a confused user.
- Finding line: pipeline.sh prints one per finding, one per line:
  `<file>:<line>: <severity> <rule-id> <problem>. <fix>.`
  Write "src/db.ts:42: high JS1 SQL from string concat. Use a bound parameter."
  Format applies only to pipeline.sh lines. Raw tool output goes to /artifacts/<tool>.log.
  If no rule id exists, omit the field.
- Agent messages (DELIVERY): no greeting, no recap, no "let me". Headings and content only.

EXIT POLICY (shared by pipeline.sh and every host script; host scripts pass it through unchanged)
0 = clean, 1 = findings, 2 = tool/infra error. Final = highest code seen (2 > 1 > 0).
- gitleaks: --exit-code 3. 3 → findings, other non-zero → infra.
- trivy:    --exit-code 0. Non-zero → infra. jq on trivy.json decides findings (section 2).
- semgrep:  --error. 1 → findings, ≥2 → infra.
- timeout:  124 → infra.
- Other tools: state their codes in Assumptions, map them the same way.
- Linters: EXIT CODES in each PROFILE section. jscpd --threshold breach = 1.
  guardrails.sh follows the same 0/1/2 policy.
- A quality gate failure (section 4) is a finding: exit 1.
- Docs and comment lint (section 4g) is WARNING only. It never changes the exit code.
  Its tool status is `warnings`, not `findings`. Exit 0 with warnings stays exit 0.
  A docs-lint tool crash is still infra: exit 2.
1) .ai-review/Dockerfile
- FROM pinned by digest. Distro-correct syntax (addgroup/adduser -S on Alpine).
- Build args come from versions.lock.json (build.sh passes them). ARG GITLEAKS_VERSION GITLEAKS_SHA256 TRIVY_VERSION TRIVY_SHA256 MIRROR_URL, and
  the same for every other tool in the lock file.
  Empty ARG fails the build: `: "${X:?}"`.
- Download from MIRROR_URL. `echo "$SHA  file" | sha256sum -c -` in the SAME RUN.
  Install to /opt/ai-review/bin, delete temp files, run `<tool> --version`.
- PATH=/opt/ai-review/bin:$PATH. Pinned tools win over bundled copies.
- Install the quality tools from the lock file the same way (mirror + SHA256, or offline
  lockfile install with --ignore-scripts / --no-index --require-hashes). Pin versions.
  Install JDK and Node only if a tool needs them. Pin versions. SwiftLint and SwiftFormat
  use the static Linux binaries from the mirror (SHA256). No Xcode or Apple SDK in the image.
  COPY lint/ and quality-gate.json and guardrails.sh → /opt/ai-review/ (read-only, root-owned).
- jq, git, coreutils `timeout` present. If one is missing, fail the build.
- OS packages: apt sources point at snapshot.debian.org with the timestamp from the
  lock file (Alpine: the pinned repository tag). Pinned versions then stay available.
- Trivy DB: COPY .ai-review/.cache/trivy → /opt/ai-review/trivy-db (read-only, root-owned).
  Check its SHA256 against the lock file in the same RUN. The DB is part of the image
  digest. No cache volume can change it.
- Package data: COPY .ai-review/.cache/data → /opt/ai-review/data (G1 index and top lists).
- COPY versions.lock.json → /opt/ai-review/versions.lock.json. Runtime checks compare with

4g. DOCS AND COMMENT LINT (ASD-STE100-based, WARNING ONLY)
Goal: flag messy docs and comments. Never block. Show the count in the summary.
- Severity: every docs finding is SARIF level `warning` (or `note`). Never `error`.
  Exit code stays 0 for warnings. Opt-in blocking: `docs.blocking: true` in
  quality-gate.json (default false). Only a human sets it.
- Scope: Markdown/text docs (*.md, *.mdx, *.txt, *.rst, docs/**), and comments in
  java, js/ts/jsx/tsx, swift, python, go files. Skip generated files, vendor dirs,
  CHANGELOG, LICENSE, lock files, and files with the header "generated".
  Diff mode: warn only on changed lines. Full mode: all lines.
- Tools (offline, config from /opt/ai-review/lint, never from /src):
    vale --config lint/vale.ini --output=JSON (comment scopes for code files; check
      which languages the installed Vale supports and list gaps in Assumptions);
    markdownlint-cli2 --config lint/markdownlint.json;
    optional lychee --offline for relative links and anchors.
  Convert JSON to SARIF with jq. Write /artifacts/docs.sarif.
- STE-lite rules (lint/styles/STE/*.yml). ASD-STE100 is a licensed standard and its full
  dictionary is not free to copy. These are approximations. Do not claim "STE compliant".
  Say "STE-lite" in output and Assumptions.
    S1  sentence > 25 words (descriptive) or > 20 words (line starts with an imperative
        verb or a list number) → warning.
    S2  paragraph > 6 sentences → warning.
    S3  passive voice ("is/are/was/were/been/being + past participle") → warning.
    S4  weak or banned words: just, simply, easily, obviously, basically, actually,
        very, really, etc., "and so on", "as needed", "if possible", "should" in a
        procedure, "may want to", utilize, leverage, "in order to", ASAP → warning.
    S5  marketing words: powerful, seamless, robust, blazing, cutting-edge, best-in-class.
    S6  idioms and phrasal-verb pairs with a simple verb (set up → configure/install,
        carry out → do, find out → learn, take out → remove) → note.
    S7  vague quantity: "a few", "several", "many", "soon", "quickly", "large" with no
        number or unit → note.
    S8  one term, many names: flag mixed terms in one file (issue/finding/alert,
        lockfile/lock file, repo/repository). Term list in styles/STE/terms.yml → note.
        terms.yml also holds the 4 axis names (security, reliability, maintainability,
        tests) and "quality gate" as the name of the whole verdict.
    S9  condition after command ("Run X if Y") in a numbered step → note.
    S10 noun cluster > 3 nouns → note (heuristic, may be wrong).
    S11 warning/caution placed after its step → note.
    S12 chatter: greeting, "let me", "I hope this helps", "in summary", "as mentioned
        above", "great question" → warning.
- Messy-doc rules (markdownlint + custom):
    D1  heading level skips (h2 → h4), duplicate headings, no top-level heading.
    D2  code fence with no language; command in prose, not in a code block.
    D3  line > 120 chars outside code, tables, and URLs; trailing spaces; mixed list markers.
    D4  broken relative link or missing anchor.
    D5  README missing: purpose line, setup, run, limits → note.
    D6  doc mentions a flag, file, or script that does not exist in the repo → warning
        (grep `--flag`, `path/file.ext` tokens in backticks against the tree).
    D7  copy-pasted paragraph (jscpd on docs, ≥ 40 tokens) → warning.
    D8  stale marker: "TODO", "FIXME", "TBD", "coming soon", "WIP" in docs → warning.
- Comment rules (vale comment scope + Semgrep generic):
    C1  comment restates the code (`// increment i` above `i++`; same words as the next
        line, ≥ 80% overlap) → warning.
    C2  comment > 15 lines in one block, or a function with a comment-to-code ratio > 60% → note.
    C3  placeholder or noise comments: "fix this", "hack", "magic", "???", "asdf", "foo",
        "temp", "test123", "stuff", "misc" → warning.
    C4  commented-out code (≥ 3 lines; same as G7, reported once under G7, not twice).
    C5  public API (exported function/class, public Java method, public Swift symbol)
        with no doc comment (Javadoc, TSDoc, DocC, docstring) → note. Skip tests and getters.
    C6  doc comment out of sync: @param/@return names not in the signature, or `@throws`
        for an exception not thrown → warning.
    C7  comment in a language other than the file default (non-ASCII letters in a
        repo whose comments are all ASCII) → note. Off by default; enable with docs.lang.
    C8  TODO/FIXME without owner or ticket (`TODO(name)` or `TODO(#123)`) → warning.
    C9  comment sentence rules S1, S3, S4 apply; skip license headers and annotations.
- Suppression: `<!-- vale off -->` / `// vale off` allowed. A suppression needs a reason
  (`vale off: quoted API text`). Without a reason → note, never error.
- Output: console summary line "docs: N warnings (S:x D:y C:z), non-blocking". Top 10
  worst files by warnings count in /artifacts/docs.log.
- Limits (state in Assumptions): heuristics make false positives. Passive-voice and
  noun-cluster checks are weak. Spelling and grammar are not checked. Docs lint cannot
  tell if the text is true.
- Axis: maintainability, warning level. It never changes the axis status.
- Registry (4h): each rule S1–S12, D1–D8, C1–C3, C5–C9 has one row (C4 uses the G7 row).
  Axis maintainability, level warning, kind heuristic, fixture in .ai-review/tests/docs/<id>.md (or code file).

4h. RULE REGISTRY (.ai-review/rules/registry.json, one source for all rules)
One row per rule, guardrail and tool check:
  {id, axis: security|reliability|maintainability|tests, tool, tool_rule, version_checked,
   level: gating|advisory|warning, kind: tool|semgrep|heuristic, fixture, sonar_key, cwe, owasp}
- `level`: gating rules fail the run. Advisory rules are reported in summary.json and
  never change the exit code. Docs rules are warning.
- `kind`: tool = a rule in a named tool; semgrep = a rule in rules/*.yaml; heuristic = a
  pattern check with known false positives. Do not claim a heuristic as full coverage.
- Architecture and library choices are advisory, not gating. Examples from PROFILE: REACT: "Redux
  Toolkit only", "forms through react-hook-form + zod", "server state through React
  Query/SWR", "no prop drilling beyond 3 levels", component file naming. Static analysis
  cannot prove them. Mark each such rule advisory in the registry.
- The lint configs, Semgrep files and guardrails.sh read rule lists from the registry or
  are checked against it (smoke R5). Add a rule = add a row + a fixture in the same change.
- summary.json groups results by `axis` from this registry.

5) GUARDRAILS FOR AI-GENERATED CODE (.ai-review/guardrails.sh + quality.yaml)
Plain bash + git + jq. Offline. Each guardrail has an id, a message with file:line,
and a test in tests/guardrails.sh. Run on the diff (diff mode) or the tree (full mode).
  G1  Hallucinated dependency: every import/require/package in changed files must be
      declared in a manifest or lock file in the repo, or be stdlib. Every NEW
      dependency in a manifest must exist in the lock file with a resolved integrity hash,
      and must be in the allowlist .ai-review/allowed-deps.txt (if the file exists).
      Typo-squat check: edit distance ≤ 2 from a popular package name = finding.
      Why: published research (USENIX Security 2025) found roughly 1 in 5 code samples from
      16 models named a package that does not exist (about 5% for commercial models). Many
      invented names repeat across runs, so attackers can register them
      ("slopsquatting"). Offline controls: (a) a new dependency must be in the allowlist
      or already resolved in the lock file with an integrity hash; (b) the name must exist in
      the package index in the image (/opt/ai-review/data/<ecosystem>-index.json, written by
      resolve.sh: every package in the repo lock files and allowlist, with first-release date,
      version dates and repository link); (c) release-age cooldown: a version younger than
      7 days (30 for new packages) = finding; (d) package with < 1 year history or no
      repository link = finding. A name not in the index (fail closed: offline, the scan
      cannot ask the registry):
        PR also adds the name to allowed-deps.txt and CODEOWNERS covers that file → status
        `review` (exit 0), with "new dependency <name>: age, history and repository not
        verified offline; reviewer checks them". The next publish job adds it to the index.
        Else → finding "unknown package <name>: add it to .ai-review/allowed-deps.txt".
      Typo-squat reference list: /opt/ai-review/data/<ecosystem>-top.txt. resolve.sh builds
      it from an official public source per ecosystem and records the URL in the lock file.
      If no official source exists for an ecosystem, the check compares against the
      index names only and says so in Assumptions; (e) install scripts forbidden: `.npmrc` must have
      `ignore-scripts=true` and `allow-git=none` (a git dependency can ship its own .npmrc
      and re-enable scripts); builds use `npm ci --ignore-scripts` (or `pnpm install
      --frozen-lockfile`), never `npm install`; (f) same rules for Maven (checksum/signature
      verification on, no unknown repositories), pip (`--require-hashes`) and go (GONOSUMDB
      unset, go.sum present).
  G2  Hallucinated API: `tsc --noEmit`, `javac` (via mvn/gradle offline, dependencies
      pre-seeded in /cache), `mypy`, `go vet` must pass. Type or compile failure = finding. Do not skip it.
      ios: G2 is NOT RUN in this pipeline (PROFILE: IOS, LIMITS).
  G3  Suppression abuse and protected files: any new suppression comment without
      `rule-id: reason` is a finding. A new suppression WITH a reason suppresses that result
      and is listed in summary.json `suppressions_new` and in the job summary for the reviewer.
      More than `guardrails.new_suppressions_max` (default 3) new suppressions in one diff =
      finding. Suppressions include the section 4b list plus `gitleaks:allow`, `trivy:ignore`,
      `# nosec`, `// vale off`.
      A change to a protected file, with or without source changes in the same diff:
        CODEOWNERS on the base branch covers the path → status `review` (warning, exit 0);
        the platform enforces the human review.
        No CODEOWNERS entry for the path → finding "protected file needs a CODEOWNERS owner".
      In diff mode the pipeline uses the base-branch copy of each protected .ai-review file.
      A PR cannot change the rules that judge it. Protected files: .ai-review/**,
      ai-review.sh, CI files (.github/workflows/**, .gitlab-ci.yml, Jenkinsfile, and the
      section 9 list), CODEOWNERS, .npmrc, .yarnrc.yml, pip.conf, settings.xml, tsconfig*.json
      strict flags, Java build logic (section 7 list), and repo copies of tool config or
      ignore files (.semgrepignore,
      .gitleaks.toml, .gitleaksignore, .trivyignore, trivy.yaml, .eslintrc*,
      eslint.config.*, .swiftlint.yml, ruff.toml, .golangci.yml, mypy.ini, .vale.ini,
      .markdownlint*). The pipeline never reads the repo copies (section 2).
  G4  Test integrity: new `.skip`, `xit`, `@Disabled`, `@Ignore`,
      `t.Skip`, `pytest.mark.skip`, `XCTSkip`, disabled tests in .xctestplan; deleted or
      weakened assertions (net negative `assert/expect` count in a
      changed test file); tests with no assertion; mocks of the unit under test.
  G5  Tests accompany code: a changed source file with logic changes needs a changed or
      new test file in the same diff. Else finding.
  G6  Diff size: > 400 changed lines or > 15 files in one change = finding "split the
      change". Limits are in quality-gate.json under "guardrails".
  G7  Dead and placeholder code: `TODO`, `FIXME`, `XXX`, `pass`-only bodies,
      `NotImplementedError`, `fatalError("TODO")`, `throw new Error("not implemented")`,
      `UnsupportedOperationException`, commented-out code
      blocks ≥ 3 lines, `console.log`/`print`/`System.out` debug output, unused exports.
  G8  Unsafe patterns AI often writes: `eval`/`exec`, `shell=True`, `innerHTML`,
      `verify=False`, `rejectUnauthorized:false`, `chmod 777`, `0.0.0.0/0`, `latest` image
      tags, `http://` URLs, `Math.random` for tokens, `md5`/`sha1` for security,
      string-built SQL, catch-and-ignore, `except:` bare, `any` casts.
  G9  Error handling and logging: every external call (http, db, fs, subprocess) has
      error handling and a timeout. No secrets, tokens, or PII in log statements.
  G10 Input validation: every new HTTP handler/route validates its input with a schema
      library already in the manifest (for example zod, joi, pydantic, bean validation,
      Codable with validation). Flag handlers that pass request data to a sink without
      validation (taint rules).
  G11 Binary and generated files: no new binary, minified, or vendored file; no file
      > 1 MB; no lock file edit without a manifest edit (and the reverse).
  G12 Provenance: a commit with a message trailer or file header marking AI authorship is
      allowed. The guardrails run the same checks. Never relax a rule for AI or
      human code.
  G13 CI and build-file hygiene (workflow files in the diff or tree; zizmor offline mode
      and actionlint when installed, else Semgrep YAML rules):
      every `uses:` pinned to a 40-char commit SHA (tag only as a comment); top-level
      `permissions: {}` or read-only with per-job scopes; no `pull_request_target` or
      `workflow_run` that checks out PR head code; no `${{ github.event.* }}` / branch /
      title / body interpolated into `run:` (pass through `env:`); no `secrets: inherit`;
      no `curl | sh`; no self-hosted runner on public PR triggers; `persist-credentials:
      false` on checkout; no long-lived cloud keys (use OIDC); no artifacts or caches
      shared across trust boundaries. Same for GitLab CI / Jenkinsfile / Dockerfile
      (`USER` set, digest-pinned FROM, no `ADD` of URLs, no secrets in ARG/ENV).
      These map to OpenSSF Scorecard checks: Dangerous-Workflow, Token-Permissions,
      Pinned-Dependencies, Binary-Artifacts, Code-Review, Branch-Protection.
  G14 Untrusted-text and agent-config safety (OWASP LLM01/LLM05/LLM06: generated or fetched
      text is untrusted input; an agent with too much power is a risk). Findings for:
      hidden or bidi Unicode (U+202A–202E, U+2066–2069, zero-width characters) in source,
      docs and agent files (AGENTS.md, CLAUDE.md, .cursorrules, .github/copilot-instructions.md,
      MCP configs); instructions in comments or docs that tell a tool to ignore rules, disable
      checks, fetch URLs, run commands or exfiltrate data; agent/MCP config granting broad
      shell, write, or network permissions or `--dangerously-skip-permissions` style flags;
      model output written straight into a shell, SQL, HTML, or file path without encoding or
      validation (improper output handling). A change to an agent-config file needs human review (like G3).
  G15 Exception handling quality (OWASP 2025 "Mishandling of Exceptional Conditions"):
      catch-and-ignore, catch that returns success, fail-open authorization on error,
      `finally` that swallows or throws, error messages that leak stack traces or internals,
      missing timeouts/retries limits/circuit breakers on remote calls, unbounded retry loops,
      resource not released on error path, generic `throw new Error()` with no cause.
  Findings are SARIF (ruleId = guardrail id, level = error). Exit by the shared policy.
  Axis per guardrail (registry.json): security = G1, G3, G8, G10, G11, G13, G14;
  reliability = G2, G9, G15; maintainability = G6, G7; tests = G4, G5. G12 is a policy
  statement with no check.

6) CODING CONTRACT (the rules AI code must follow before it is written)
Emit this block in the quality.yaml header comment AND in the --help output, so a coding
agent can read it (no separate file):
  - Smallest change that solves the task. Reuse existing helpers; search before adding.
  - One responsibility per function/class. ≤ 50 lines, ≤ 4 params, nesting ≤ 4.
  - Depend on abstractions; inject dependencies; no hidden globals.
  - No duplicated logic; extract at the third copy. No magic numbers or literal URLs.
  - Handle every error path. Validate every external input. Parameterize every query.
  - No new dependency without need; prefer stdlib. Never invent an API: verify it exists.
  - Never edit lint, CI, or gate config to make code pass. Never skip or weaken a test.
  - Add or update tests for every behavior change. Keep names clear; no abbreviations.
  - Write docs and comments in WRITING STYLE. One idea each. Explain why, not what.
    No filler, no greeting, no recap. Keep code, paths and flags exact.
    Keep docs true: update them in the same change as the code.

7) ai-review.sh (host bootstrapper)
- set -euo pipefail. HOME_DIR = the directory of this script (`${BASH_SOURCE[0]}`).
  Run "$HOME_DIR/.ai-review/doctor.sh --need scan" first. Non-zero → exit 2.
  Read image.ref and versions.lock.json from HOME_DIR, not from the repo. In CI, HOME_DIR
  is the base-branch copy (section 9). Locally, HOME_DIR is the repo root.
- cd "$(git rev-parse --show-toplevel)". mkdir -p .ai-review/.cache .ai-review/artifacts.
- Image ref, first non-empty wins: AI_REVIEW_IMAGE, .ai-review/image.digest (local build),
  .ai-review/image.ref (committed, written by the publish job). Empty → exit 2
  "run .ai-review/resolve.sh and build first". Reject a ref without @sha256:.
  `docker image inspect "$IMAGE"` fails → exit 2 "load image first".
- Limits from env (defaults): AI_REVIEW_MEMORY=4g, AI_REVIEW_CPUS=2, AI_REVIEW_TMP_SIZE=2g,
  AI_REVIEW_TIMEOUT=3600 (whole run, seconds), AI_REVIEW_TOOL_TIMEOUT=900 (per tool).
  Validate each value with a regex. Bad value → exit 2.
- /src is always read-only. `--fix` makes pipeline.sh write /artifacts/fix.patch. The host
  script then runs `git apply --check` and `git apply` on that patch. It does not commit.
  `--update-baseline` makes pipeline.sh write /artifacts/baseline.json. The host script
  copies it to .ai-review/baseline.json and prints the diff. It does not commit.
- `--coverage PATH`: mount each file read-only at /coverage/ (section 2).
- Two stages, two containers (TRUST MODEL):
    Stage 1 "build" (only when java is detected): compiles the repo offline (with Error
      Prone and NullAway where PROFILE: JAVA injects them). It runs no tests. It gets /src:ro,
      /cache, and an empty `$TMPDIR/ai-review-build` as /out. No /artifacts mount.
    Stage 2 "scan": all scanners, the gate and the summary. It gets /out:ro as untrusted
      data: compiled classes and the compiler log. SpotBugs and ArchUnit read the class
      files as bytecode; they do not run them. pipeline.sh validates the compiler log
      format and ignores any other file in /out.
    Limit (state in --help): the repo build controls stage 1. A malicious build can hide
    its own compile errors or ship classes that differ from the source. G3 protects the
    build logic (build.gradle*, settings.gradle*, buildSrc/, gradle/, .mvn/, and the
    <build>, <plugins>, <pluginRepositories>, <repositories>, <profiles> parts of pom.xml).
    A human then reviews each change to it.
- Common docker run flags for both stages:
    docker run --rm --pull=never \
      --user "$(id -u):$(id -g)" \
      --memory "$AI_REVIEW_MEMORY" --memory-swap "$AI_REVIEW_MEMORY" \
      --cpus "$AI_REVIEW_CPUS" --pids-limit 512 \
      --cap-drop ALL --security-opt no-new-privileges \
      --read-only --tmpfs "/tmp:rw,nosuid,size=$AI_REVIEW_TMP_SIZE" \
      --network none \
      -v "$PWD:/src:ro" \
      -e AI_REVIEW_LANGS -e AI_REVIEW_TIMEOUT -e AI_REVIEW_TOOL_TIMEOUT \
      "$IMAGE" --stage build|scan "$@"
  Stage 2 adds `-v "$PWD/.ai-review/artifacts:/artifacts"`.
  The cache mount: stage 1 only (/cache for m2, gradle, npm). Stage 2 needs no cache.
- Capture the exit code: `rc=0; docker run ... || rc=$?`. Stage 1 exits 0 when the build
  ran (a compile error is data for G2 in stage 2) and 2 on infra error. Final = stage 2 code,
  or 2 if stage 1 failed. The host script never changes 0/1/2.
- Exit 137 (out of memory) → exit 2 with "raise AI_REVIEW_MEMORY".

9) CI INTEGRATION (the tool wires itself into the CI the repo already uses)
Contract for every CI: fetch base branch → run ./ai-review.sh → read exit code (0/1/2)
→ upload SARIF + artifacts. No CI-specific logic lives in pipeline.sh.
- `./ai-review.sh --init-ci [auto|github|gitlab|generic] [--write]`:
  - auto: detect from repo files, first match wins, log "ci detected: <name>":
      .github/workflows/        → github
      .gitlab-ci.yml            → gitlab
      Jenkinsfile               → generic (emit a stage snippet)
      bitbucket-pipelines.yml, azure-pipelines.yml, .circleci/config.yml,
      .buildkite/              → generic (emit a step snippet)
      none found                → generic, plus print "no CI found".
    If no CI file exists, also read the remote URL (`git remote get-url origin`):
    github.com → github, gitlab → gitlab.
  - Without --write: print the snippet and the target path (dry run, default).
  - With --write: create a NEW file only (.github/workflows/ai-review.yml,
    .gitlab/ai-review.gitlab-ci.yml + one `include:` line printed for the user to add).
    Never edit or overwrite an existing CI file. Existing target → exit 2 with the path.
- Auto-offer after setup. The user needs no knowledge of --init-ci:
    build.sh succeeds → it runs `./ai-review.sh --init-ci auto` (dry run).
    It shows the CI found, the target path and the snippet.
    TTY → ask one question: "Add ai-review to <ci> at <path>? [y/N]". Default no.
      y → run `./ai-review.sh --init-ci auto --write`. Print the new file path and the next
      git commands (add, commit). Do not commit or push.
      N → print the two manual commands (--init-ci, --init-ci --write) and stop.
    Non-TTY, no --write-ci → do not write. Print the snippet and the two manual commands.
    build.sh --write-ci → write with no prompt (for agents and CI bootstrap).
    Target file exists → do not ask. Print "ai-review already in CI: <path>".
    Record the answer in .ai-review/.cache/ci-offer.json. Do not ask again after a "N".
    The manual commands always work, also after a "N".
- Templates in .ai-review/ci/ must follow guardrail G13: actions pinned by full SHA
  (resolved by resolve.sh from the action's latest release tag, tag kept as a comment),
  `permissions: {}` then per-job minimum, no `pull_request_target`, no untrusted
  `${{ }}` in `run:`, `persist-credentials: false`, `fetch-depth: 0`.
- Trusted inputs in the scan job (TRUST MODEL). On a PR, the job extracts these files from
  the base branch into "$RUNNER_TEMP/trusted/" with the same layout, not from the PR checkout:
    ai-review.sh, .ai-review/doctor.sh, .ai-review/image.ref, .ai-review/versions.lock.json
    (`git show "origin/$BASE_REF:<path>" > "$RUNNER_TEMP/trusted/<path>"`).
  Then it runs "$RUNNER_TEMP/trusted/ai-review.sh" from the repo root. No script from the
  PR checkout runs before or during the scan. cosign verify uses the identity in the
  trusted lock file. Rules, lint config and the gate live in the image.
- Before the scan, the job installs dependencies with scripts off (section 2) and runs the
  repo tests that write coverage. These steps run PR code. They run before the scan, with
  no secrets and read-only permissions, and they cannot change the trusted files.
  Pass each coverage file with --coverage.
- Each scan job runs `.ai-review/doctor.sh --need ci --plan` (base-branch copy) first. Missing
  tool → fail fast. Do not install tools in a scan job. Prepare the runner image instead.
- Each template must do, per provider:
  github:  trigger pull_request + push to default branch; `git fetch origin $BASE_REF`;
           run diff mode on PRs, full scan on push to default and on a weekly schedule;
           pull the image by digest and run `cosign verify` with the identity in the lock
           file before the scan; upload each *.sarif with github/codeql-action/upload-sarif
           (category = tool name), needs security-events: write; upload artifacts; job
           summary from summary.json (one line per axis).
           Fork PRs: no secrets, no `security-events: write`. Skip upload-sarif when
           `github.event.pull_request.head.repo.full_name != github.repository`. Keep the
           artifacts upload and the exit code. Never use pull_request_target.
           Code scanning on private repos needs GitHub Advanced Security. Without it, skip
           upload-sarif, keep artifacts, and print "code scanning not enabled".
           SARIF upload limits (file size, results per run, runs per file): read them from
